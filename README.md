# Лабораторная работа: Docker & Docker Compose

## Часть 1: Dockerfile

### Сравнение конфигураций

```dockerfile
# Использование старой версии без контроля обновлений
FROM debian:wheezy 

# Задание пользователя по имени, а не по UID
RUN useradd foo

# VOLUME объявлен до того, как в папку были записаны данные
VOLUME /data

# Эти команды не сохранятся в образе (выполняются в слое тома)
RUN touch /data/x
RUN chown -R foo:foo /data

USER foo
CMD ["ls", "-l", "/data"]
```

### Исправления

```dockerfile
# теперь используем конкретную стабильную версию 
FROM debian:bookworm-slim

# теперь создаем пользователя с явным UID 
RUN groupadd -g 1001 foo && useradd -u 1001 -g foo -m foo

# сначала создаем структуру папок и меняем права, и только потом объявляем VOLUME
RUN mkdir -p /data && touch /data/x && chown -R 1001:1001 /data

# теперь VOLUME фиксирует состояние папки с уже созданными файлами
VOLUME /data

USER 1001
CMD ["ls", "-l", "/data"]
```


1. Устаревший или неопределённый образ: FROM debian:wheezy
   
   В книге “Использование Докер” Эдриена Моуэта в образце используется debian wheezy, но насколько я поняла, эта версия уже не поддерживается. Docker не проверяет наличие новой версии образа при каждой сборке, если тег уже есть локально
    
   Исправление: использован современного образа: FROM debian:bookworm-slim
   
   Результат: Сборка стала предсказуемой
   

2. Установка прав через имя пользователя, а не UID
   
   Команда: RUN useradd foo и USER foo
   
   В Docker идентификаторы пользователей внутри контейнера совпадают с UID на хост-машине. Однако имена пользователей (например, foo) могут соответствовать разным UID в разных дистрибутивах из-за чего может возникнуть конфликт прав
   
   Исправление: пользователь создается и назначается с явным указанием UID: RUN useradd -u 1001 foo
   
   Результат: права доступа на файлы будут предсказуемыми внутри контейнера и при работе с томами на хосте
   

4. Объявление VOLUME до завершения настройки папки
   
   Команда: VOLUME /data (расположенная перед RUN touch...)
   
   Инструкция VOLUME создает точку монтирования. Все команды RUN, идущие после этой инструкции в Dockerfile, выполняются уже во временном томе. Как только этот шаг сборки завершается, временный том удаляется вместе со всеми изменениями
   
   Исправление: инструкция VOLUME перенесена в самый конец файла, после всех команд mkdir, touch и chown
   
   Результат: файл x и правильные права доступа при запуске контейнера они будут доступны пользователю
   


### Плохие практики при работе с контейнерами
1. Ручное внесение изменений в работающий контейнер
    
   Пользователь запускает контейнер из хорошего образа, заходит в него через docker exec -it <container_id> bash и начинает вручную править конфиги. Но любые ручные правки исчезнут безвозвратно, как только контейнер будет удалён, его нельзя буде воспроизвести автоматически  

   Любые изменения должны фиксироваться в Dockerfile, после чего образ пересобирается, а старый контейнер заменяется новым  


2. Хранение важных данных внутри изменяемого слоя контейнера
   
   Плохо запускать контейнер с базой данных или приложением, которое сохраняет пользовательские файлы прямо в свою файловую систему без использования внешних томов. Файловая система контейнера не предназначена для хранения постоянных данных: она медленнее обычных дисков, данные в ней привязаны к жизненному циклу конкретного контейнера. При удалении старого контейнера и запуске нового из нового образа (обновлении версии приложения) все накопленные данные будут удалены  

   Нужно использовать флаг -v или секцию volumes в Compose. Важные данные должны находиться на внешних томах  


## Часть 2: Docker Compose
### Сравнение конфигураций
```
docker-compose.yml

# использование устаревшей версии формата
version: '2' 

services:
  database:
# плавающий тег latest, в связи с чем непредсказуемая сборка, которая может вызвать несовместимость версий
    image: postgres:latest     
environment:
# хранение пароля в открытом виде
      - POSTGRES_PASSWORD=secret     
# избыточный проброс портов (получается, что база доступна и из внешней сети)
ports:
      - "5432:5432" 
  web-app:
# плавающий тег latest, в связи с чем непредсказуемая сборка, которая может вызвать несовместимость версий
    image: nginx:latest
    depends_on:
      - database
# отсутствие явного разделения сетей

```

### Исправления
```
docker-compose.yml
# более новая версия
version: '3.8'

services:
  database:
# фиксация версии и типа образа, гарант того, что БД не обновится внезапно. 
# 'alpine' - это сверхлегкий дистрибутив, который уменьшает размер образа и количество уязвимостей 
    image: postgres:15-alpine
    environment:
# вместо передачи пароля напрямую, передача адреса файла, где записан пароль
      - POSTGRES_PASSWORD_FILE=/run/secrets/db_password
    secrets:
# указание контейнеру, какой именно секрет должен быть смонтирован в его файловую систему
      - db_password
    networks:
# помещаем базу в закрытую сеть
      - backend_net

  web-app:
# использование конкретной версии, будет работать одинаково у всех разработчиков
    image: nginx:1.25-alpine
    depends_on:
      - database
    networks:
# изоляция: веб-сервер находится в своей сети Т
      - frontend_net

secrets:
# опять же пароль из файла, а не в открытом виде
  db_password:
    file: ./db_password.txt

# изоляция сетей
networks:
  frontend_net:
    driver: bridge
  backend_net:
    driver: bridge

```
1. Использование устаревшей версии формата
   
   Команда: version: '2'  

   Старые версии формата Compose ограничивают использование современных функций безопасности и управления ресурсами  

   Исправление: версия обновлена до version: '3.8'  

   Результат:  использование современных инструкций для безопасного хранения паролей  


2. Использование «плавающих» тегов (latest)
   
   Команда: image: postgres:latest и image: nginx:latest  

   Тег latest не гарантирует конкретную версию программного обеспечения, что делает сборку непредсказуемой  

   Исправление: указаны конкретные версии образов на базе легковесного дистрибутива: postgres:15-alpine и nginx:1.25-alpine  

   Результат: у всех участников проекта запускается одна и та же версия ПО  


3. Хранение секретов в открытом виде
   
   Команда: POSTGRES_PASSWORD=secret в разделе environment  

   Переменные окружения отображаются в открытом виде при выполнении команды docker inspect, сохраняются в истории команд, пароль легко может быть украден  

   Исправление: механизм secrets и переменная POSTGRES_PASSWORD_FILE  

   Результат: пароль передается в контейнер в виде временного файла в оперативной памяти (/run/secrets/), который недоступен через стандартные команды контейнеров  


4. Избыточный проброс портов базы данных
   
   Команда: ports: - "5432:5432" для сервиса database  

   Проброс портов на хост-машину делает базу данных доступной из внешней сети, что не способствует безопасности  

   Исправление: секция ports удалена, доступ через изолированные внутренние сети  

   Результат: база данных менее уязвима  


5. Отсутствие явного разделения сетей
 
   Команда: Отсутствие раздела networks у сервисов

   По умолчанию Docker Compose помещает все контейнеры в одну общую сеть, то есть при получении доступа к одному контейнеру получаем доступ сразу ко всей сети  

   Исправление: созданы две независимые сети frontend_net и backend_net, сервисы разнесены по разным сетям  

   Результат: реализована сетевая изоляция  


 
## Сетевая изоляция
```
services:
  database:
    image: postgres:15-alpine
    networks:
# База только в своей сети
      - backend_net  

  web-app:
    image: nginx:1.25-alpine
    networks:
# Веб-сервер только в своей сети
      - frontend_net 

networks:
  frontend_net:
# Отдельный виртуальный мост
    driver: bridge   
  backend_net:
# Отдельный виртуальный мост
    driver: bridge   
```

При выполнении команды:

```
docker-compose exec web-app ping database
```
система выдает ошибку, что подтверждает успешную изоляцию сервисов друг от друга:

